# PWA notes: install, updates and the kill switch

This file is the standing reference for the installable game. Every phase that ships content ships it through the service worker described here, so read it before changing anything in `vite.config.js`, `src/pwa/` or `.github/workflows/deploy.yml`.

## What ships

- A service worker at `/pilgrims-predestined-path/sw.js` with scope `/pilgrims-predestined-path/`, generated by vite-plugin-pwa (`generateSW`, `registerType: 'prompt'`).
- `manifest.webmanifest` with id `/pilgrims-predestined-path/`, name "The Pilgrim's Predestined Path" and short_name "Pilgrim's Path".
- Four icon PNGs in `public/` (`pwa-192x192.png`, `pwa-512x512.png`, `maskable-icon-512x512.png`, `apple-touch-icon-180x180.png`), all generated once from `public/favicon.svg`.
- The code lives in `src/pwa/updates.js` (waiting-update controller), `src/pwa/install.js` (install row logic), `src/pwa/startHandoff.js` (carries the pilgrim count across an update reload) and `src/pwa/store.js` (the two singletons). `src/main.jsx` is the only file that imports the plugin's registration module, so no test loads it.

## Standing rules

These keep installed copies working for years. Break one and players are stuck on a build you cannot reach.

1. Never rename `sw.js`, change its scope, or change the manifest `id`. Installed clients remember all three.
2. Every storage key and every custom cache name starts with `ppp:`. All projects on avocadopanic.github.io share one origin, so an unprefixed key can collide with another project. Store preferences only, never anything a player would be upset to lose or anything another project could misread.
3. Keep `cleanupOutdatedCaches: true` in the workbox options so old precaches are removed when a new worker takes over.
4. Keep `registerType: 'prompt'`. Never add worker takeover (`skipWaiting`, `clientsClaim`) or any automatic update mode. An update applies only when the player presses Start on the setup screen, so a game in progress is never reloaded.
5. Test the worker with `npm run build` followed by `npm run preview`. Never test it under `vite dev`; the dev server does not serve the real worker.
6. Offline completeness and the offline notice belong to Phase 7. Phase 2 only guarantees install and safe updates.

## Build id

The setup screen footer shows `v`, a 7-character git SHA and the UTC build date. Local development and the test runner show `dev`. Use it to answer "which version is this?" when someone reports a problem. The id is not shown during play or on the end screen.

## Deploy policy

- A push that changes only `.planning/**`, `docs/**`, `**/*.md` or `.claude/**` does not deploy. Any other changed file deploys.
- To redeploy by hand (for example after a docs-only change that must go live, or to retry after an Actions outage), use the workflow's "Run workflow" button. The trigger is `workflow_dispatch`.
- Deploys queue instead of cancelling: a running deploy always finishes and the next one waits.
- Every code deploy changes the build id and the worker file, so returning players see the update hint on their next visit to the setup screen.
- After each deploy, CI fetches the live manifest, `sw.js` and the four icons with a cache-buster and fails the run if any of them is not served under the base path.
- The first docs-only push after this phase should show no new deploy run. Check with `gh run list --workflow deploy.yml`. GitHub's `**/*.md` filter is expected to match Markdown at the repository root; this is where that is confirmed live.

## Icons

- The PNGs come from `public/favicon.svg` through `scripts/pwa-assets.config.mjs` (padding 0, background #0a0608, full-bleed, no transparency).
- The one-time command is:

  ```
  npx --yes --ignore-scripts @vite-pwa/assets-generator@1.0.2 --config scripts/pwa-assets.config.mjs
  ```

- Run a package legitimacy check first (registry version, install scripts, maintainers). The generator pulls in sharp, whose own install script is the reason for `--ignore-scripts`.
- Never add the generator to `package.json` or the lockfile. It is an author tool, not a dependency.
- Re-run it only if `public/favicon.svg` changes. Then check sizes and opacity (the build test does this) and look at the four images yourself.

## Two-deploy update check (required in the verification of Phases 3 to 7)

A service worker update cannot be proven by one build. Every phase that ships to players repeats this check.

1. Deploy build A and open it, once in a desktop browser and once as an installed phone app.
2. Start a game in one window and leave a second window on the setup screen.
3. Deploy build B with a visible change.
4. On the setup window the hint "A new version will load when you start." appears. Pressing Start loads B and begins the chosen game.
5. The game in progress is never reloaded. After it ends, Play Again shows the hint, and Start loads B.
6. On an installed phone app, close the app fully and reopen it to trigger the check. The in-app visibility check runs at most once every 30 minutes.
7. A plain browser reload may also load B while a worker waits. That is the player's own reload and is fine; do not treat it as a failure, and do not assume a reload keeps the old version.

## Real-device checklist

- Android Chrome and desktop Chrome or Edge: the setup screen shows "Install this game"; after installing, the app opens the live URL in its own window with the gold cross icon, and the button is gone.
- iPhone or iPad Safari: the setup screen shows "On iPhone or iPad: tap Share, then Add to Home Screen"; Add to Home Screen gives the gold cross icon with the label "Pilgrim's Path"; the icon opens the game; inside the installed app the install row is hidden.

## Kill switch (emergency only)

### When to use it

Only when a broken worker keeps players on a bad build and a normal deploy cannot reach them. It is a last resort, not a way to force an update.

### Side effects

- It reloads every open window, games in progress included.
- It deletes all Cache Storage for avocadopanic.github.io, not only this game's caches. Other projects hosted on the same origin lose theirs too.
- The vite-plugin-pwa docs advise leaving the stub deployed for a long time, because you cannot know which version a given player has installed.

### Procedure (two keys, one commit)

1. In one commit, set `const KILL_SWITCH = true;` in `vite.config.js` and `const EXPECT_KILL_SWITCH = true;` in `src/build-output.test.js`. Either key alone fails CI by design, so a single accidental flip cannot ship the stub.
2. Push only with the owner's go-ahead.
3. After the deploy, confirm the live `sw.js` contains `unregister`. In DevTools Application, one reload later there should be no service worker and empty Cache Storage.
4. Keep the stub deployed until the fix is ready. Do not change other plugin options while it is up.
5. Ship the fix with both keys set back to false in the same commit, then run the two-deploy update check above.
